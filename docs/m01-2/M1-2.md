### **2. Năng lực cần đạt**

Kết thúc hai tuần, bạn cần làm được năm việc:

1. Hiểu client-server communication và HTTP request/response ở mức cơ chế.
2. Thiết kế REST-style API cơ bản cho Events và Bookings.
3. Tự viết HTTP server bằng thư viện chuẩn của Node.js, không sử dụng framework.
4. Chuyển implementation sang NestJS và nhận diện những gì framework đã làm thay mình.
5. Dùng `curl` và Browser DevTools để quan sát một request thực tế thay vì chỉ suy luận từ code.

### **3. Các prerequisite cần bổ sung**

Tôi sẽ coi những kiến thức sau là có thể bạn chưa nắm vững, dù đã gặp chúng trong quá trình học TypeScript hoặc làm Backend trước đây.

| Prerequisite        | Mục tiêu                                                     |
| ------------------- | ------------------------------------------------------------ |
| Client-server model | Hiểu client và server là hai chương trình giao tiếp với nhau |
| TCP/IP cơ bản       | Hiểu IP address, port, connection ở mức khái niệm            |
| JSON                | Serialization và deserialization                             |
| TypeScript modules  | Import/export, tổ chức code                                  |
| Node.js runtime     | Biết cách chạy ứng dụng Node.js                              |
| Async JavaScript    | Hiểu Promise, async/await và xử lý I/O bất đồng bộ           |

Đặc biệt, cần phân biệt hai điều:

- HTTP server không đồng nghĩa với một ứng dụng Express/NestJS.
- HTTP không đồng nghĩa với TCP. HTTP là giao thức tầng ứng dụng, sử dụng transport bên dưới để truyền dữ liệu.

### **4. Phạm vi cần giới hạn**

Trong hai tuần này, không cần đào sâu:

- TCP internals, packet retransmission, congestion control.
- TLS cryptography và chi tiết certificate validation.
- HTTP/2, HTTP/3, QUIC.
- WebSocket, SSE, Long Polling.
- Proxy, reverse proxy, load balancing.
- Authentication, Authorization.

Chúng sẽ xuất hiện ở những milestone sau. Với DNS, TCP và TLS, chỉ cần đạt Understanding và có thể quan sát được khi trace request.

### **2. Chi tiết từng unit**

**U1 — HTTP mental model**

Các kiến thức cần nắm:

- Client và server là hai chương trình độc lập.
- Request-response model.
- HTTP nằm ở application layer.
- HTTP/1.1 message structure.
- Request line, status line, headers, body.
- Content negotiation ở mức cơ bản: `Accept`, `Content-Type`.
- Statelessness.
- Phân biệt HTTP, HTTPS, TCP và IP.

Một HTTP/1.1 message có thể hình dung:

```
POST /events HTTP/1.1
Host: localhost:3000
Content-Type: application/json
Accept: application/json

{
  "title": "Backend Conference"
}
```

Response:

```
HTTP/1.1 201 Created
Content-Type: application/json
Location: /events/123

{
  "id": "123",
  "title": "Backend Conference"
}
```

Bạn cần hiểu mỗi phần có vai trò gì, ai tạo ra chúng và ai đọc chúng. RFC 9112 mô tả cấu trúc message HTTP/1.1, còn RFC 9110 mô tả semantics ở mức giao thức.&#x20;

**U2 — HTTP semantics và API design**

Đây là unit quan trọng nhất về mặt tư duy API.

Cần nắm:

- Resource là gì, cách biểu diễn resource bằng URI.
- Phân biệt GET, POST, PUT, PATCH, DELETE.
- Safe method và idempotent method.
- Status code phản ánh kết quả xử lý như thế nào.
- Headers và body sử dụng vào mục đích gì.
- API không nên phụ thuộc vào việc client có gọi endpoint theo đúng thứ tự hay không.

Đặc biệt, phải thực sự phân biệt hai thuộc tính:

| Method | Safe  | Idempotent     |
| ------ | ----- | -------------- |
| GET    | Có    | Có             |
| POST   | Không | Không mặc định |
| PUT    | Không | Có             |
| PATCH  | Không | Không mặc định |
| DELETE | Không | Có             |

Đây là semantics chuẩn của HTTP, không phải quy ước tùy ý của NestJS. Một API vẫn có thể định nghĩa POST hoặc PATCH theo cách idempotent, nhưng không được mặc định điều đó chỉ từ tên method.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://www.rfc-editor.org\&sz=32)

rfc-editor.org+1



Bạn cần xử lý được các trường hợp như:

- POST tạo resource mới.
- PUT thay thế resource.
- PATCH cập nhật một phần resource.
- DELETE resource.
- Client gửi lại request do không nhận được response.
- Resource không tồn tại.
- Resource tồn tại nhưng thao tác không hợp lệ ở trạng thái hiện tại.

**U3 — Native Node.js HTTP Server**

Đây là nơi chuyển kiến thức thành năng lực.

Công nghệ: TypeScript + Node.js built-in `node:http`.

Không dùng Express hoặc NestJS.

Các thành phần cần làm quen:

- `http.createServer()`.
- `IncomingMessage`.
- `ServerResponse`.
- `server.listen()`.
- `req.method`, `req.url`, `req.headers`.
- Đọc request body.
- Parse JSON và serialization.
- Routing và route parameters.
- Thiết lập response status code, headers và body.

Một điểm cần chú ý: Node.js đã xử lý việc nhận và phân tích HTTP protocol ở tầng server. Bạn không phải tự parse raw TCP packet trong milestone này. Việc tự làm TCP server sẽ thuộc M3.2.&#x20;

**U4 — Testing & correctness**

Không chờ đến khi có database mới bắt đầu kiểm thử backend.

Cần biết:

- Test một request thành công.
- Test request thiếu dữ liệu.
- Test JSON không hợp lệ.
- Test resource không tồn tại.
- Test method không được hỗ trợ.
- Test response status, headers và body.
- Phân biệt lỗi đầu vào với lỗi nội bộ server.

Một bảng mapping ban đầu nên có:

| Tình huống                                    | Status code |
| --------------------------------------------- | ----------- |
| Đọc thành công                                | 200         |
| Tạo thành công                                | 201         |
| Xóa thành công, không trả body                | 204         |
| JSON không hợp lệ                             | 400         |
| Resource không tồn tại                        | 404         |
| Method không được hỗ trợ                      | 405         |
| Xung đột trạng thái hoặc dữ liệu              | 409         |
| Payload hợp lệ về cú pháp nhưng sai ngữ nghĩa | 422         |
| Lỗi ngoài dự kiến                             | 500         |

Đối với payload validation, một số API quy ước dùng 400 thay cho 422. Trong project này, hãy chọn một quy ước nhất quán và ghi rõ lý do.&#x20;

**U5 — Networking: DNS → TCP → TLS → HTTP**

Đây là phần cần xây dựng mental model, không cần tự triển khai.

Hãy hiểu thứ tự và vai trò:

```
User enters URL
       |
       v
Parse URL
       |
       v
DNS Resolution
       |
       v
IP Address
       |
       v
TCP Connection
       |
       v
TLS Handshake (HTTPS)
       |
       v
HTTP Request
       |
       v
Server Processing
       |
       v
HTTP Response
       |
       v
Client Receives Response
```

Cần hiểu:

- DNS giúp tìm IP từ domain name.
- TCP thiết lập connection giữa client và server.
- TLS thiết lập kênh giao tiếp được mã hóa và xác thực server.
- HTTP sử dụng connection để trao đổi request/response.
- Timing của DNS, connection, TLS, TTFB và response download khác nhau như thế nào.

Không cần đào sâu thuật toán của TCP hoặc cryptography. Những nội dung đó có milestone riêng.

**U6 — Port sang NestJS**

Sau khi đã hiểu và có native implementation, chuyển cùng API sang NestJS.

Các thành phần:

| NestJS concept       | Vai trò cần nắm                        |
| -------------------- | -------------------------------------- |
| Module               | Tổ chức thành phần ứng dụng            |
| Controller           | Mapping route và tiếp nhận request     |
| Provider / Service   | Chứa logic xử lý                       |
| Dependency Injection | Nest quản lý và cung cấp dependency    |
| Middleware           | Xử lý request trước route handler      |
| Exception handling   | Chuyển lỗi thành HTTP response         |
| Serialization        | Tạo response từ giá trị handler trả về |

Không cần học tất cả tính năng trên ở mức sâu.

Hãy quan sát request lifecycle của NestJS: middleware → guards → interceptors → pipes → controller → service → response. Chỉ controller, service và một middleware nhỏ cần được thực hành trực tiếp; guards, interceptors, pipes chỉ cần định vị vai trò.&#x20;

```
curl -v https://example.com
```

So sánh thông tin của hai lệnh.

#### **Buổi 3 — Thiết kế API contract cho Booking v0**

Khoảng 1,5 giờ · Apply

Bây giờ mới bắt đầu nghĩ đến tính năng.

Mô hình dữ liệu tối giản:

```
type Event = {
  id: string;
  code: string;
  title: string;
  startsAt: string;
};

type Booking = {
  id: string;
  eventId: string;
  customerName: string;
};
```

Không thêm inventory, thanh toán, user authentication hoặc database.

Thiết kế các endpoint:

| Resource | Endpoint        | Method                  |
| -------- | --------------- | ----------------------- |
| Events   | `/events`       | GET, POST               |
| Event    | `/events/:id`   | GET, PUT, PATCH, DELETE |
| Bookings | `/bookings`     | GET, POST               |
| Booking  | `/bookings/:id` | GET, PUT, PATCH, DELETE |

Với mỗi endpoint, mô tả:

- Input và output.
- Status code thành công.
- Các lỗi có thể xảy ra.
- Business rule tối thiểu.
- Trường hợp request được gửi lặp lại.

Một business rule nhỏ để thực nghiệm conflict: `Event.code` phải duy nhất.

**Đầu ra**

API contract dạng Markdown. Chưa cần OpenAPI/Swagger vì phần đó thuộc M5.1.

#### **Buổi 6 — DNS, TCP, TLS và vòng đời request**

Khoảng 1,5 giờ · Learn + Verify

**Nội dung học**

Đặt vấn đề: Khi trình duyệt gọi `https://example.com`, request có thể đến server bằng cách nào?

Học:

- URL gồm những thành phần gì.
- Domain resolution.
- DNS cache ở mức khái niệm.
- IP address và port.
- TCP connection.
- TCP three-way handshake ở mức khái niệm.
- TLS handshake ở mức khái niệm.
- HTTP request sau khi connection được thiết lập.

Không đào sâu các packet và thuật toán mã hóa.

**Thực hành**

Tự giải thích vai trò từng bước, cũng như việc bước nào thuộc DNS, bước nào thuộc transport và bước nào thuộc application protocol.

| Thành phần            | Native Node.js        | NestJS                           |

Có ba điều tôi muốn nhấn mạnh khi thực hiện M1.2.

**Thứ nhất: Đừng học NestJS trước Node.js HTTP.**

Đây là điều kiện để không biến mình thành developer chỉ biết sử dụng framework. Bạn cần tự tạo được một request handler, tự đọc request và tự gửi response trước khi NestJS xuất hiện.

**Thứ hai: Đừng cố xây Booking thành sản phẩm hoàn chỉnh.**

Booking v0 chỉ cần chứng minh bạn biết xây một HTTP service. In-memory storage là có chủ đích. Không PostgreSQL, không TypeORM, không authentication, không Docker trong milestone này.

**Thứ ba: Hãy xem request/response là một sợi chỉ xuyên suốt cả năm.**

Khi học database, bạn sẽ hiểu request tương tác với DB. Khi học concurrency, bạn sẽ hiểu nhiều request cùng chạy. Khi học networking và production, bạn sẽ hiểu request đi qua những thành phần nào và có thể thất bại ở đâu.

M1.2 là bước chuyển từ *viết chương trình* sang *xây dựng một Backend Service*. Đừng vội vàng vượt qua bước chuyển này.

**Điểm bắt đầu:** Buổi 1 — Client-server và HTTP mental model. Hoàn thành sơ đồ request-response trước khi viết bất kỳ dòng code Booking nào.
